# ForgeIQ — Implementation & Design Plan

## Product and architecture

ForgeIQ is a manual-input-first manufacturing scheduling workspace. It will show no fabricated operational data; sample data appears only after an explicit action and is deterministic, labelled and removable. The recommendation is a transparent ranking of actual feasible schedules, not a trained model or LLM output.

- **Frontend:** React, Vite, TypeScript, Tailwind CSS, Recharts, Lucide icons, custom SVG Gantt and browser tests for critical interactions. Accessible CRUD forms and responsive left-sidebar navigation.
- **Backend:** Python 3.11+, FastAPI, Pydantic, SQLAlchemy, Alembic and python-dotenv. A root `.env` is loaded for local use without overriding host-provided values. SQLAlchemy uses `backend/data/forgeiq.db` by default for Windows-local development; configured external database URLs support managed MySQL preview or production PostgreSQL with fail-closed certificate and hostname verification. A recorded additive Alembic migration runs at startup and through an explicit local init command; tests only use isolated SQLite and never touch the shared managed database.
- **Serving:** Vite development server proxies `/api` to FastAPI. In preview and packaged deployment, the compiled `frontend/dist` is served by FastAPI on configured port 3000 and API calls remain same-origin. Deployment notes cover Vercel static frontend with `VITE_API_URL`, Render/container FastAPI backend, persistent storage and managed PostgreSQL. CORS uses an explicit configurable origin list, not a permissive wildcard in production.
- **Persistence:** SQLAlchemy models for jobs, machines, operations, schedule runs, scheduled operations, algorithm results and recommendation details. Each run carries a versioned input snapshot. Mutations increment a dataset version; prior schedules remain retrievable but are clearly marked stale.
- **Scheduling engine:** Deterministic, event-time list scheduling for the parallel-machine and precedence-aware job-shop scenarios with machine eligibility, release times, machine calendar bounds, setup/processing durations and no machine overlap. FCFS, SPT, EDD, Priority and LPT choose from currently precedence-ready operations. A separate permutation-flow-shop mode makes NEH applicability explicit; NEH is never represented as a general job-shop optimizer. Add bounded A*, Uniform-Cost, Greedy Best-First, Breadth-First and Depth-First state-space searches that share the same hard-constraint action generator, canonical state hashing, duplicate-state checks, measured limits/status, complete-schedule validation and objective-weighted cost. A* uses only documented admissible lower bounds and claims optimality only when search proves it within the configured limits. Keep search metadata alongside each persisted result.
- **Automotive knowledge model:** Extend jobs with component type/status, machines with processing capabilities and maintenance windows, and operations with an optional required capability. Keep existing `product_name` and API records backward-compatible with safe defaults. Add explicit Engine Block (Milling → Drilling → Inspection), Crankshaft (Turning → Grinding → Inspection) and Brake Disc (Turning → Drilling → Inspection) demonstration workflows through an opt-in, removable, clearly simulated automotive sample; never imply proprietary specifications. Represent `Compatible`, `Precedes`, `Available`, `Finished` facts and schedule-validity rules in `backend/app/scheduling/knowledge.py`. Represent each machine assignment as an action with preconditions/effects in `planning.py`; the search expands only applicable planning actions.
- **Automotive/A* integration:** Add `backend/app/scheduling/search.py` for immutable search states, cost/bounds, priority queues and termination. Extend `engine.py` as the single scheduling entry point; extend `validation.py` through the knowledge model; support saved maintenance calendars in every applicable algorithm. Update `schemas.py`, `models.py`, `routes.py` and a new additive Alembic migration for component/status/capability/maintenance/required-capability fields. Dynamic rescheduling reuses the same search action engine and search bounds/weights, while retaining frozen completed/in-progress operations, machine outages, event audit, immutable parent runs and transactional urgent-order persistence.
- **Frontend/teaching UI:** Keep existing routes/navigation and styling. Add automotive type/status/capability/maintenance fields and an explicit automotive demo action in the existing data/workspace screens; add optional workflow step assistance to operation entry. Extend the existing scheduling screen with selectable A*/UCS/Greedy/BFS/DFS, bounded search controls, non-negative cost weights and a visible knowledge/planning explanation. Extend saved result comparisons/CSV with expanded nodes, generated states, measured runtime and termination/optimality status. Show automotive component names and A* statistics only from actual persisted results. Extend the existing rescheduling form to select search methods and pass limits/weights; do not create a second scheduler or rewrite the application.
- **Dynamic rescheduling add-on (source: user-provided `AI_Manufacturing_Workflow_Dynamic_Job_Scheduling_Project.pdf`, sections 7, 12–15 and 17):** Add a separate operator-triggered event workflow to an existing feasible saved Job Shop or Single-Operation/Parallel-Machine run. Reuse the already implemented supported dispatch rules; add no untrained ML model or unimplemented Genetic Algorithm. Support breakdown, scheduled maintenance, an actual processing delay, an urgent multi-operation order and an operator-reported high-risk machine. Keep previous runs immutable; protect operations completed before the event and unaffected work already in progress; model recovery/outage windows, preserve precedence/capacity/machine compatibility, and reoptimize remaining work. Persist each event, its parent/revised runs, affected/moved work and a measured stability score. Show before/after Gantts, metric changes and a plain-language cause/explanation.
- **Reports:** Interactive machine-row Gantt generated from returned schedule records; algorithm comparison table/charts, deterministic recommendation, selected-run persistence, CSV exports and print stylesheet.
- **Validation:** pytest against isolated SQLite fixtures, frontend tests, type/build checks and API smoke checks. Report only checks actually run.

## Scheduling rules and result semantics

- Dataset validation checks empty inputs, duplicate IDs, missing references, dates, positive durations, eligible available machines, sequence/predecessor consistency and cycles before any run.
- The two core scenarios are a single-operation parallel-machine problem and ordered job-shop scheduling. The extra permutation-flow-shop scenario is explicit so NEH has a supported, testable place; selection cards disclose scenario applicability.
- FCFS, SPT, EDD, Priority and LPT use deterministic documented tie-breakers and respect current eligibility, precedence and release/calendar constraints. For job-shop, priority rules guide ready-operation dispatch; they are heuristics, not optimality proofs. NEH is permutation-flow-shop only. A non-preemptive operation that cannot fit a machine's configured availability window is infeasible for that candidate; unavailable machines cannot be selected.
- A* and the additional search methods represent a node as scheduled/completed operation assignments, per-machine free times, per-job operation progress and accumulated weighted cost. An applicable `Perform Operation` action assigns a ready operation to a capability-compatible available machine, then records completion/progress effects. The scalar search cost is a non-negative weighted sum in minutes for makespan, total tardiness, avoidable machine-gap idle, setup/changeover and operator-reported machine-risk penalties. Its per-job remaining-work estimates are lower bounds; A* optimality is claimed only for a complete search with a certified bound. UCS, Greedy, BFS and DFS retain their own queue criteria and never inherit an A* optimality claim. Configurable expansion/time limits return explicit stats and status; if stopped before a complete goal, no partial schedule is emitted.
- Knowledge predicates are generated from actual user records: `Compatible(operation,machine)` checks the explicit eligible-machine list and any required processing capability; `Precedes(a,b)` is the ordered operation dependency; `Available(machine,time)` checks the availability flag/window and maintenance calendar; `Finished(operation,time)` comes from an actual schedule completion. Logical rules validate one machine operation at a time, predecessor completion before start, compatibility, machine availability, uniqueness/completeness and immutable completed production work during rescheduling.
- Automotive demonstration templates are configurable learning examples, not certified process plans: Engine Block = Milling → Drilling → Inspection; Crankshaft = Turning → Grinding → Inspection; Brake Disc = Turning → Drilling → Inspection. Component/status/capability/calendar additions use safe migration defaults for pre-existing generic records. The demo is user-invoked, labelled simulated and removable.
- All time values in a result are minutes from the declared scheduling-horizon origin. Operations have actual start/end/minutes, job/machine IDs and scenario; job completion is the final operation completion. Due dates are soft evaluation criteria unless explicitly defined otherwise.
- Metrics define makespan as last completion minus horizon origin; total completion as the sum of completion offsets from that origin; tardiness as positive completion-minus-due; max lateness as the maximum signed completion-minus-due; tardy count as jobs with positive lateness; waiting as accumulated job/operation queue intervals, excluding machine idle; utilization as productive time divided by the machine's available horizon after unavailable intervals. N/A is used where a denominator or comparison is not meaningful.
- The recommendation filters infeasible runs, ranks the selected primary metric in the correct direction, then uses documented deterministic tie-breaks (secondary objectives, followed by a stable algorithm-name ordering). The UI states the measured comparison, objective, and “Best among the feasible algorithms evaluated for this dataset. This is not a guarantee of global optimality.”

## Design system

- **Design movement:** Contemporary Swiss industrial instrumentation—orderly, high-contrast and precise, softened for day-to-day usability.
- **Core principles:** operational clarity over decoration; strong information hierarchy; visible constraints and traceability; consistent, accessible interactions.
- **Color philosophy:** warm near-white and pale steel surfaces reduce visual fatigue; deep navy anchors trust and legibility; clear cobalt is ForgeIQ's ownable action color; green/amber/red are reserved for true status and feasibility feedback.
- **Layout paradigm:** fixed, compact left rail and a broad workbench canvas. Data-entry and results use vertically structured, task-focused panels, not a decorative dashboard-card grid. The timeline takes the width it needs and scrolls horizontally when necessary.
- **Signature elements:** ForgeIQ wordmark with a simple interlocking forge/flow-line glyph; cobalt hairline section markers; monospaced time and metric labels reminiscent of calibrated controls.
- **Interaction philosophy:** edits are explicit, validated inline, and preserve user input after errors. Schedule runs have visible progress and current/outdated state. Selecting a Gantt bar opens its actual details; keyboard focus and labels remain visible.
- **Animation:** restrained 120–180 ms fades/position changes for navigation and status; no looping or distracting motion; respect `prefers-reduced-motion`; timeline zoom remains direct and predictable.
- **Typography system:** IBM Plex Sans for product/UI text with a clear semibold heading hierarchy; IBM Plex Mono for IDs, timestamps, durations and numeric metrics; robust system fallbacks.
- **Brand essence:** a dependable scheduling workbench that turns a manufacturer's entered constraints into inspectable, comparable plans; **precise, practical, transparent**.
- **Brand voice:** concise and operational, explaining outcomes without AI hype. Examples: “No manufacturing data available. Add jobs and machines to begin scheduling.” “SPT produced the lowest makespan among the feasible schedules evaluated.”
- **Wordmark & logo:** custom inline SVG mark formed by two linked production-flow segments inside a squared forge frame, paired with the ForgeIQ wordmark; no generic gear/photo decoration.
- **Signature brand color:** Forge cobalt `#2563EB`, reserved for primary actions, active navigation and selected schedule accents.

## Automotive/A* syllabus mapping and scope boundaries

The course demonstration maps A* evaluation to `f(n)=g(n)+h(n)` (accumulated non-negative user-weighted scheduling cost plus an admissible remaining-work lower bound); UCS to minimum `g(n)`; Greedy Best-First to minimum `h(n)`; BFS/DFS to their respective frontier order. Planning preconditions/effects are exercised by every search successor, while the knowledge base exposes the facts and rules used to validate actual results. Dashboard values (search states, elapsed time and termination) are measured from runs, never seeded/hardcoded. A reproducible demo starts from the opt-in automotive sample, compares AI searches with FCFS/SPT/EDD/Priority/LPT under identical inputs, then applies an operator-entered breakdown or maintenance event to a selected saved schedule and compares before/after Gantts.

No generic factory dashboard, auto-created machines/jobs, default sample records, fake statistics, hardcoded schedule/recommendation, random failures, AI chatbot, unrelated inventory/billing/payment/employee functions, fabricated ML, or nonfunctional controls. No claim of globally optimal job-shop schedules. Platform auto-publishing is off; this task builds and verifies a preview, not a public production release.

The requested dynamic-rescheduling increment remains an operator-triggered simulation and schedule revision. Machine-risk events are explicitly user-reported inputs, not sensor inference or an ML prediction. Use implemented search/baseline algorithms; do not claim or silently substitute a Genetic Algorithm. Do not delete existing CRUD, baseline scheduler views, metrics, authentication, routes, styling, deployment, stored input records or original saved schedule behavior; use one additive migration and keep every sample opt-in/removable.

## Additive AI intelligence implementation decisions
- Search instrumentation is optional and is attached to the shared existing search algorithm path; without a trace collector the scheduler remains on its existing code path. Trace storage is in-memory, TTL/cap bounded and process-local.
- AI analysis reads current entered records or existing saved-run snapshots; it introduces no dataset registry, database tables, Alembic revisions, packages or lockfile changes.
- Method comparisons run scenario-applicable algorithms on the selected source and use existing schedule ranking; infeasible outputs are excluded and objective values—not unlike search-internal `g/h/f`—drive business recommendations.
- Deterministic agent outputs remain advisory and read-only. Existing dynamic rescheduling remains the only schedule-changing route and receives explicit operator confirmation.
- Bayesian risk inference uses exact enumeration over documented illustrative binary assumptions. It is not factory-trained or validated and cannot mutate availability or schedules.
- New views use lazy navigation, existing UI styling conventions, SVG and an additive `ai.css`; responsive rules already in `responsive.css` remain unchanged.
